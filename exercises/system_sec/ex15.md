# Exercise 15.a — Remote Logging with rsyslog

Configure your Ubuntu Desktop to send all log entries to the Ubuntu Server in real time.

## Configure the RECEIVER (Ubuntu Server)

SSH into your server from Desktop, or work directly on the Server VM.

```bash
ssh ekko@172.16.121.131
```

### Verify rsyslog is installed

```bash
rsyslogd -v
```

Expected output: something like `rsyslogd 8.x.x ...` — it's already installed on Ubuntu by default.

---

### Edit rsyslog config to listen for incoming logs

```bash
sudo cp /etc/rsyslog.conf /etc/rsyslog.conf.bak   # backup first!
sudo nano /etc/rsyslog.conf
```

Find these lines near the top (they're commented out by default) and **uncomment** them:

For **UDP** (faster, no delivery guarantee):
```
module(load="imudp")
input(type="imudp" port="514")
```

For **TCP** (preferred — guaranteed delivery):
```
module(load="imtcp")
input(type="imtcp" port="514")
```

> **Why TCP over UDP?**
> UDP is fire-and-forget — log entries can be lost if the network is busy.
> TCP guarantees every entry arrives in order. For security logging, a missing entry = a gap in your evidence.

Uncomment **both** if you want, but TCP is the one to use.

---

### Restart rsyslog on the server

```bash
sudo systemctl restart rsyslog
sudo systemctl status rsyslog
```

Check it's `active (running)` with no errors.

---

### Verify port 514 is now open on the server

```bash
sudo ss -tulnp | grep 514
```

Expected: lines showing rsyslog listening on port 514 for UDP and/or TCP.

---

## Configure the SENDER (Ubuntu Desktop)

Switch to your **Ubuntu Desktop** now.

### Create a forwarding config file

```bash
sudo nano /etc/rsyslog.d/10-remote.conf
```

Add this single line to forward everything to your server:

For **UDP:**
```
*.* @172.16.121.131:514
```

For **TCP** (preferred — note the double `@@`):
```
*.* @@172.16.121.131:514
```

> `@` = UDP, `@@` = TCP. One extra `@` = one extra guarantee.

Save and exit (`Ctrl+X`, `Y`, `Enter`).



### Restart rsyslog on the Desktop

```bash
sudo systemctl restart rsyslog
sudo systemctl status rsyslog
```



## Test It

### Generate a test log entry on the Desktop

```bash
logger "TEST: Hello from Ubuntu Desktop - rsyslog exercise 15.a"
```

`logger` manually injects a message into the syslog system.

---

### Check the log arrived on the Server

Switch to your **Ubuntu Server** and run:

```bash
sudo tail -f /var/log/syslog
```

You should see your test message appear within a second or two.

If you want to search specifically:
```bash
sudo grep "TEST" /var/log/syslog
```

---

### Explore the rsyslog config file

Back on either machine, look at the default config:

```bash
cat /etc/rsyslog.d/50-default.conf
```

This file controls what gets logged where. A few interesting lines to highlight and comment on:

| Line | What it means |
|------|---------------|
| `auth,authpriv.*  /var/log/auth.log` | All authentication events go to auth.log |
| `*.*;auth,authpriv.none  /var/log/syslog` | Everything except auth goes to syslog |
| `kern.*  /var/log/kern.log` | Kernel messages go to kern.log |
| `mail.*  /var/log/mail.log` | Mail server events go to mail.log |


### Top-3 good points about rsyslog

1. **Tamper-evident logging** : remote logs cannot be altered from a compromised local machine. If local and remote logs differ after an incident, the difference reveals what the attacker tried to hide.
2. **Centralised visibility** : all servers in a company can forward to one log server, giving one place to search across the whole infrastructure.
3. **Black box effect** : even if the local server is completely destroyed or unbootable, the remote log still contains everything that happened right up until the crash.



# Exercise 15.b — Security Auditing with Lynis

**Goal:** Audit three different systems (Desktop, Server, Metasploitable2) and compare the results.



## Install Lynis

Lynis needs to be installed on each machine you want to audit.

### On Ubuntu Desktop and Ubuntu Server:

```bash
sudo apt update && sudo apt install lynis -y
```

Verify:
```bash
lynis --version
```

### On Metasploitable2:

Metasploitable2 may not have Lynis in its repos. Install manually:

```bash
cd /tmp
wget https://downloads.cisofy.com/lynis/lynis-3.1.4.tar.gz
tar xvf lynis-3.1.4.tar.gz
cd lynis
```

> If wget doesn't work due to network restrictions in your lab, you can copy the tarball from the Desktop using SCP:
> `scp lynis-3.1.4.tar.gz msfadmin@172.16.121.136:/tmp/`



## Run a Lynis Audit

Run this on **each machine** in turn:

```bash
sudo lynis audit system
```

This takes 1–3 minutes. Lynis will scroll through many checks.



## Read the Results

### Option 1 — Check the log directly

```bash
sudo grep -E "Warning|Suggestion" /var/log/lynis.log
```

### Option 2 — Look at the end of the terminal output

Lynis prints a summary at the end with:
- **Warnings** — things that are actively wrong and should be fixed
- **Suggestions** — improvements that would strengthen security

### Option 3 — Read the full log

```bash
sudo less /var/log/lynis.log
```


## Audit 1 — Ubuntu Desktop

Run on your Desktop, note down 3–5 warnings/suggestions and research what each one means.

Example warnings you might see and what they mean:

| Warning / Suggestion | What it means | Why it matters |
|---|---|---|
| `FIRE-4512 - No firewall detected` | iptables has no rules set | Open to all incoming connections |
| `AUTH-9286 - No password aging configured` | Passwords never expire | Compromised creds stay valid forever |
| `SSH-7408 - SSH root login is allowed` | sshd_config has PermitRootLogin yes | Direct root access over network |
| `PKGS-7392 - Outdated packages found` | Unpatched software | Known CVEs are exploitable |
| `LOGG-2190 - No remote logging configured` | Logs only stored locally | Attacker can delete evidence |


## Audit 2 — Ubuntu Server

SSH into the server and repeat:

```bash
sudo lynis audit system
sudo grep -E "Warning|Suggestion" /var/log/lynis.log
```

Note whether the server has **fewer** warnings than the Desktop — it should, because servers are typically more minimal.

## Exercise 15.c — Can Lynis Audit Application Configs?

**Question:** If you have CRM or billing software installed — can Lynis audit that too?

**Answer:**

- **A bit of yes** : Lynis checks if SW is installed and notes it. Can flag outdated versions.
- **Mostly no** : Lynis does not understand app specific configs.
It won't know if your CRM has weak API keys, no rate limiting, or misconfigured roles.
- **What you need instead:** App specific audit tools, manual security review, or pen testing of app layer.
- **The principle:** Lynis covers the **OS layer**. The app layer is a separate security domain requiring separate tools.
